# 日常アプリ

ブラウザだけで動く小さなアプリ。サーバー側の処理もアカウント登録もなく、データは端末の中だけに残る。

| アプリ | 用途 | 場所 |
| --- | --- | --- |
| 冷蔵庫の在庫・賞味期限管理 | 食材の期限管理、バーコードでの登録、食品ロスの記録 | `apps/fridge/` |
| 書類・回覧・会議の期限トラッカー | 提出期限のある書類・回覧・申請と会議の予定の管理 | `apps/docs-tracker/` |
| 備蓄・消耗品の管理 | 在庫が少なくなったものと期限が近いものの通知 | `apps/stock/` |
| 家計簿 | レシートの合計額の記録、費目別の内訳、明細CSVの取り込み | `apps/kakeibo/` |
| ポイントカード | カード・会員証の撮影保管、バーコードの画面表示 | `apps/cards/` |

## iPhone で使う（GitHub Pages で公開する）

カメラ（バーコード読み取り）とオフライン起動は、ブラウザの決まりで `https://` でしか動かない。
そのため、このリポジトリでは **GitHub Pages に公開して iPhone から開く**方法をとる。

`.github/workflows/pages.yml` が `main` への変更を検知して自動で公開する。
公開されるのは **2つのアプリとトップページだけ**で、テストや設定ファイルは含まれない。

### 初回だけ必要な操作（リポジトリの管理者）

1. GitHub の **Settings → Pages** を開く
2. **Source** を「GitHub Actions」にする
3. `apps/` 以下の変更を `main` に反映する（Actions タブで公開の進行を確認できる）

公開先のURL：

| | URL |
| --- | --- |
| トップページ | `https://akihitofujioka-bit.github.io/myproject/` |
| 冷蔵庫 | `https://akihitofujioka-bit.github.io/myproject/fridge/` |
| 書類トラッカー | `https://akihitofujioka-bit.github.io/myproject/docs-tracker/` |
| 備蓄・消耗品 | `https://akihitofujioka-bit.github.io/myproject/stock/` |
| 家計簿 | `https://akihitofujioka-bit.github.io/myproject/kakeibo/` |
| ポイントカード | `https://akihitofujioka-bit.github.io/myproject/cards/` |

### iPhone のホーム画面に追加する

1. **Safari** で上のURLを開く（Chrome など他のブラウザからは追加できない）
2. 下部の共有ボタン（□に↑）→「ホーム画面に追加」
3. 追加されたアイコンから起動する

初回にバーコードを読み取るとき、カメラの使用許可を聞かれるので「許可」を選ぶ。
Android の Chrome では、メニューの「アプリをインストール」から同じことができる。

### 公開範囲について

- 公開されるのは**アプリの画面（HTML・JavaScript・アイコン）だけ**。入力したデータは各自の端末に残るので、公開されない
- このリポジトリはもともと公開設定のため、Pages の有効化によってコードの公開範囲は変わらない
- URLを知っていれば誰でもアプリの画面自体は開ける（他人が開いても、その人の端末には何のデータもない状態で始まる）

## パソコンだけで試す場合

各フォルダの `index.html` をダブルクリックすれば、カメラとホーム画面追加を除く機能が使える。
同じネットワークの端末から見るなら、リポジトリ直下で次を実行して `http://<IPアドレス>:8080/apps/fridge/` を開く。

```
npx http-server . -p 8080
```

## バーコード読み取り（冷蔵庫アプリ）

下部の「バーコードで追加」からカメラを起動し、商品のJANコードを読み取る。

**読み取りの仕組み**は2段構え。

1. 端末が `BarcodeDetector` API に対応していれば、それを使う（Android の Chrome など。OS標準の処理で精度が高い）
2. 非対応の端末（iPhone の Safari など）では、`apps/fridge/ean.js` の自前デコーダで読む

どちらでも読めないときのために、**番号の手入力**を常に用意している。誤読を防ぐため、
同じ番号を2回続けて読み取れたときだけ確定する。

**商品名は端末の中で覚える。** 外部の商品データベースには問い合わせない（通信を一切しない設計のため）。
そのため、初めて読むバーコードは品名を1回だけ入力する必要がある。次回から同じ商品は
品名・単位・保管場所が自動で入る。覚えた対応は「JSONで保存」に含まれるので、端末を移しても引き継げる。

**制約**：自前デコーダは JAN-13／JAN-8／UPC-A に対応。暗い場所、光の反射、曲がった面、
手ブレでは読み取れないことがある。読めないときは明るい場所で、バーコードを枠いっぱいに、
端末を10〜15cm離して静止させる。それでも読めなければ番号を手入力する。

## カレンダーに登録して通知を受け取る

iPhone の Safari には、アプリだけで「3日後に鳴らす」という通知の仕組みがない。
そこで**端末の標準カレンダーに期限を渡し、iOS 標準の通知で知らせる**方式をとっている。

- 書類トラッカー：各書類の「カレンダー」ボタン、または「未処理の期限をカレンダーに登録」
- 冷蔵庫：「期限が近い食材をカレンダーに登録」（期限が7日以内のもの）

通知は**前日の同じ時刻と当日**の2回。書類は9時、食材は18時（夕食の支度前）に設定している。

押すと iPhone では共有シートが開くので「カレンダー」を選ぶ。共有シートが使えない環境では
`.ics` ファイルとして保存されるので、それを開くとカレンダーに取り込める。

同じ書類を登録し直すと、予定の識別子（UID）が同じで更新番号（SEQUENCE）だけが進むため、
カレンダー側は**同じ予定の更新**として扱う。ただしカレンダーアプリによっては
新しい予定として追加されることがあるので、期限を何度も変更した場合は重複を確認してほしい。

生成部分は `apps/shared/ics.js`（RFC 5545 準拠、外部通信なし）。

### 撮り方（無音カメラ／書類カメラ）

撮影は2種類あり、画面で選べる（`apps/shared/camerapref.js`。選んだ内容は端末に残り、どのアプリでも同じ設定が使われる）。

| | 無音で撮る（既定） | 自動で切り出す |
|---|---|---|
| シャッター音 | 鳴らない | **鳴る**（日本向け iPhone では消せない） |
| 書類の四隅 | 自分で枠に合わせる | 自動で見つけて歪みも直す |
| 仕組み | 映像の1コマを取り出す（`SilentCameraViewController`） | VisionKit の書類カメラ |

会議中や窓口では無音、家で腰を据えて読み取るときは自動切り出し、という使い分けを想定している。

## 会議の通知の読み取り

- 開催日は**「日時」の欄を先に探す**。行頭に「1 」「(1) 」「・」が付いていても拾う
- 「日時」の欄が無いときは、**時刻が併記された行**の日付を採る。それも無ければ確度を「低」にして画面で確認を促す
- 冒頭の**発信日は開催日にしない**。以前は行頭の番号のせいで「日時」の行と気づけず、発信日（多くは当日）を開催日にしていた（2026-09-24 修正）

## カレンダーへの書き込み（重複させない）

iPhone アプリでは、会議も期限も **EventKit でカレンダーへ直接書き込む**（`apps/shared/calendarwrite.js`）。

- 共有シート（「カレンダーに追加」を選ぶ画面）は出ない
- 書き込んだ予定の識別子を `docs-tracker.v1` の `calIds` に覚えておき、次回は**同じ予定を書き換える**。登録し直しても予定が増えない
- 会議の識別子は「開催日＋会議名」から作る。以前は登録するたびに変わる値を使っていたため、更新のたびにカレンダーに同じ予定が増えていた（2026-09-24 修正）
- ブラウザで開いているとき、またはカレンダーの利用を断られたときは、これまでどおり `.ics` ファイルを渡す経路に切り替わる

### 期限の登録先（通知かカレンダーか）

iPhone アプリのときは登録先を選べるようにしてある。

- **「期限を通知に登録」** … アプリから直接通知する（カレンダーには入らない）
- **「期限をカレンダーにも入れる」** … 予定として入る。**Apple Watch の文字盤（コンプリケーション）はカレンダーの予定を見ているため、手首に締切を出したいときはこちら**

ブラウザで開いているときは通知の仕組みが無く、どちらを押しても同じ動きになるため、2つめのボタンは出さない。

### 通知の文面（Apple Watch 向け）

iPhone アプリとして動いているときは、カレンダーではなく**端末の通知**に登録する。
その文面は Apple Watch で 1 行目と 2 行目だけ見れば判断できる形にしている。

```
明日：【回覧】○○協議会の回答
提出先：総務課 ／ 状態：未着手
```

1行目は `apps/shared/native.js` の `whenLabel()`（本日／明日／3日後／1か月後…）と件名、
2行目は各アプリが渡す `summaryLine`（書類は提出先と状態、会議は時刻・場所・懇親会、
食材と備蓄は残数と置き場所）。設定手順は `docs/apple-watch-event-haptics.md` にまとめてある。

## Apple Watch へ送る一覧

`apps/shared/watch.js` が、どのアプリを開いていても全体の一覧を組み立て、iPhone アプリの
WatchBridge プラグイン経由で Apple Watch に渡す（ブラウザで開いているときは何もしない）。

- 送るのは**今日から1週間先の会議**・**2週間先までの期限**（過ぎたものも残す）・**買い物リスト**で、それぞれ最大20件
- 送る先は Apple Watch だけで、外部のサーバーには送らない（iPhone と Watch の直接通信）
- 送る時機は「画面を開いたとき」「画面を閉じるとき」「各アプリの `save()`」
- Watch 側のアプリ（SwiftUI）は `mobile/ios/App/WatchAppSources/`。導入手順は `docs/apple-watch-app.md`

## 買い物リスト（リマインダー経由）

冷蔵庫の「使い切ったものを買い物リストへ」と、備蓄の「補充が必要なものを買い物リストへ」は、
iPhone の**リマインダー**に品名を送る。Apple Watch のリマインダー App で消し込めるようにするため。

- Web からリマインダーへ直接書き込む方法は無いため、**ショートカット App を経由する**（`apps/shared/reminders.js`）。利用者が一度だけショートカットを作る必要がある（手順は `docs/apple-watch-shopping-list.md`）
- ショートカットが無い環境（パソコンのブラウザ）では、品名をクリップボードにコピーするだけに切り替わる
- 冷蔵庫が送るのは「直近2週間で使い切り、いま在庫に無いもの」。**廃棄したものは送らない**（買い直すとは限らないため）
- 備蓄が送るのは「最低在庫数を下回ったもの」で、「品名 あと○個」の形にする
- 送るのは品名だけで、外部への通信は行わない

## 家計簿の考え方

レシートの**合計額だけ**を記録する方式にしている。品目ごとの明細を取ろうとすると入力の手間が増えて続かなくなるためで、月ごとの傾向をつかむには合計で足りるという判断による。

- **費目は店名から推定する。** その店で過去にいちばん多く使った費目を選び、履歴が無い場合は店名に含まれる語（「スーパー」「薬局」「病院」など）から推す
- **カード・電子マネーの明細は CSV で取り込める。** 日付・内容・金額の列を指定する方式で、列の並びは自動で推測する。日本の明細に多い Shift_JIS も読める。同じ日付・金額・店名の記録は二重に入らない
- **レシートのバーコードは使っていない。** レシートに印字されているのは取引番号で、金額も品目も含まれていないため
- **iPhone アプリではレシートを撮って合計・日付・店名を自動入力できる（第2段階）。** 撮影は VisionKit の書類カメラ、文字認識は Vision（`mobile/ios/App/App/ReceiptScannerPlugin.swift`）。どちらも端末内で完結する。認識した行から合計・日付・店名を取り出す規則は `apps/shared/receipt.js` にあり、`apps/tests/receipt.test.mjs` で検証している
- 読み取り規則を実物のレシートで確かめるには、写真を `mobile/tools/ocr-probe.swift` に通すと、アプリと同じ認識結果（JSON）が得られる。それを `receipt.test.mjs` の fixture に加えれば、アプリを作り直さずに規則を直せる

費目別の内訳は、費目ごとに色を分けず**単色の横棒**で表している。1系列（金額）の大小を比べるだけなので、色を分けても情報が増えず、どの色がどの費目かを覚える手間だけが増えるため。

### レシートから買ったものを送る

家計簿でレシートを撮ると、合計・日付・店名に加えて**買ったものの一覧**（品名と値段）が出る。
送るものにチェックを付けて「冷蔵庫へ」「備蓄へ」を押すと、そのアプリの在庫として登録される。

- 送り先の台帳には**足すだけ**で、既にある項目には触れない
- 送り先のデータが読めない形になっている場合は、**何も書かずに中止する**（上書きで台帳を壊さないため）
- 賞味期限はレシートに載らないため空で入る。送った先のアプリで入れる
- 仕組みは `apps/shared/inbox.js`。アプリはどれも同じ場所（localStorage）にそれぞれの鍵で保存しているため、鍵と形を合わせて足している

### 書類を撮って写真に保存する（書類トラッカー）

回覧や掲示物を撮って、iPhone の写真アプリに保存する。VisionKit の書類カメラを使い、
四隅を自動で見つけて歪みを直す。**アプリとして開いたときだけ**表示される。

- **シャッター音は鳴らない。** 書類カメラは静止画撮影の API ではなく映像から1コマを切り出す
  仕組みのため、標準のシャッター音が鳴らない（Apple 純正の「メモ」の書類スキャンと同じ）。
  こちらで音を消しているわけではない
- 写真への**追加だけの許可**（`NSPhotoLibraryAddUsageDescription` / `PHPhotoLibrary` の addOnly）
  を求める。既存の写真を読むことはない
- 撮った画像はアプリ内には残らず、写真アプリにだけ保存される
- 実装はレシート撮影と同じプラグイン（`ReceiptScannerPlugin`）の `scanToPhotos`。
  プラグインを増やすと登録漏れが起きやすいため、動作している1つに寄せている

### 会議の通知を読み取って登録する（書類トラッカー）

開催通知を撮ると、**会議名・日付・時刻・場所・懇親会の有無**を読み取り、確認してから
端末のカレンダーとアプリの両方に登録できる。**アプリとして開いたときだけ**表示される。

- 1枚に複数の会議が載っている場合（「1 〇〇委員会」「2 〇〇委員会」）は**会議ごとに分けて**読み取る
- 読み取った内容は**必ず画面で確認・修正してから**登録する。通知の書き方は文書ごとに違うため
- 年の書かれていない日付（「10月15日」）は、いちばん近い年を当てはめたうえで**注意書きを出す**
- カレンダーには予定として入り、**前日と開始30分前**に通知する
- アプリには種別「会議」の項目として入る（期限＝開催日、提出先＝場所、メモに時刻と懇親会の有無）
- 読み取りの規則は `apps/shared/meeting.js`。令和の年号、「午後1時30分」「14:00～16:00」、
  「会 場」のように字の間に空白が入る書き方に対応している

## データの保存場所と安全性

- データは**開いたブラウザの localStorage にのみ**保存される。外部への送信は一切行わない（通信するコードを含まない）
- したがって**ブラウザや端末が変わるとデータは引き継がれない**。「JSONで保存」で書き出し、移行先で「JSONから読み込み」する
- ブラウザの「閲覧履歴・サイトデータの削除」を実行するとデータも消える。定期的な書き出しを勧める
- シークレットウィンドウでは、閉じた時点でデータが消える
- **共用パソコンでは使わない**。使う場合は終了時にサイトデータを削除する
- 書類トラッカーには、個人が特定できる情報（氏名・住所・個人番号など）を入力しない。書類名は「〇〇申請書（△△課分）」のような表記にとどめる
- 公開する場所に置く場合でも、**公開されるのはアプリの画面だけで、入力したデータは公開されない**（データは各自の端末に残るため）

## 朝のブリーフとの連携

書類トラッカーの「JSONで保存」で書き出したファイルを `data/deadlines.json` として置くと、`/brief`（朝のブリーフ）が今日の締切として拾う。
冷蔵庫アプリの書き出しを `data/fridge.json` に置き、`brief.config.json` の `fridge.enabled` を true にすると、期限が近い食材も1行だけ添えられる。

`data/` の中身は業務情報を含みうるため git 管理対象外にしてある。

## つくりの方針

- 依存ライブラリなし。ビルド不要。通信なし
- 端末の設定に合わせてダークモードに対応
- 画面幅に合わせて可変。入力欄は16px以上（iOSで勝手に拡大されないため）
- アプリを更新したときは、次に開いたときに反映される（Service Worker がまずキャッシュを返すため）
