# 逐語録（全文議事録）の作り方

議会の委員会は一言一句の記録が要る。要約では足りないので、文字起こしを全文取る。
2台のデバイスで同じ会議を録っている場合は、それを1本にまとめる。

**これは日報・週報とは別の成果物。** 日報は「何が決まったか」を数行にするもので、
逐語録は「誰が何を言ったか」を落とさず並べるもの。混ぜない。

決定的な処理は `scripts/merge_transcripts.py` が持つ。このファイルは**判断の方**を書いている。

---

## 大前提

- **完成品ではない。** 出てくるのは音声認識の生の並びで、校正済みの議事録ではない。
  固有名詞・数字・団体名の誤りは必ず残る。人が音声を聴いて直すための土台。
- **本文を書き換えない。** 誤字に見えても直さない。印を付けて人に渡す。
  勝手に直すと、直した箇所が正しいのか元がそうだったのか誰にも分からなくなる。
- **業務情報を含む。** 出力先の `reports/verbatim/` は `.gitignore` 済み。
  コミットしない。Drive にも自動では上げない（日報・週報とは扱いが違う）。

## 2台の録音は「同じものが2つ」ではない

開始・停止は手押しなので、同じ会議でも録れている範囲が食い違う。
2026-08-27 の常任委員会では、片方が**冒頭16分を録り逃していて**、
最初のセグメントが既に議事の途中から始まっていた。

したがって必要な操作は単純な結合ではない。**カバー範囲の広い方を主とし、
欠けている区間だけをもう片方で埋める。**

---

## 手順

### 1. 対象の録音を特定する

`references/collection.md` の「1. PLAUD」に従って `list_files` で拾い、
**時間帯が重なる録音を同じ会議として束ねる**（開始時刻の差では判定しない）。

### 2. 全文を取る

```
get_transcript(file_id, block="transaction_polish", limit=200)
```

- **`block` は `transaction_polish`。** 整文済みでフィラーが落ち、話者ラベルと
  タイムスタンプが残る。議事録の土台にはこれを使う。`transaction`（生）は
  言い淀みが多く読めない、`outline` は要約なので全文にならない。
- レスポンスに `total` が入る。`next_cursor` が `null` になるまで回し、
  **集めたセグメント数が `total` と一致することを確認する。**
  スクリプトもこれを検証して、足りなければ警告を出す。
- `limit` は最大500まで通る。実測では76分・130セグメントの会議を1回で取得できた
  （2026-08-28 に確認）。ただし1回の返り値が大きくなるとツール出力の上限に当たるので、
  **既定は200にして `next_cursor` で回す**方が安全（同じ上限に `get_file` が実際に当たっている）。
- この規模なら全文取得は軽い。実績：34分=107、61分=98、76分=130セグメント。

### 3. 作業ファイルに落とす

録音1本につき1ファイル、`reports/verbatim/.work/<label>.json` に置く。
`pages` には `get_transcript` の応答を**そのまま**入れる（加工しない）。

```json
{
  "label": "A",
  "file_id": "5cc7789927d2ed7379f37f2dd56ca395",
  "name": "08-27 会議: ...",
  "start_at": "2026-08-27T04:25:23Z",
  "duration_ms": 4589000,
  "pages": [ { "total": 130, "segments": [ ... ] } ]
}
```

`start_at` と `duration_ms` は `list_files` の値をそのまま写す。
**`start_at` は UTC。** `segment.start_time` はその録音の開始からの相対ミリ秒なので、
録音どうしで直接比較できない。絶対時刻に直すのはスクリプトの仕事
（`start_at + start_time/1000`）。ここで自分で計算し直さない。

### 4. 整列と欠落を見る

```
python3 .claude/skills/report/scripts/merge_transcripts.py analyze \
    reports/verbatim/.work/rec_a.json reports/verbatim/.work/rec_b.json
```

出るもの：録音ごとのカバー範囲、録音どうしの重なり、主録音の推奨、
主録音に欠けている区間、話者ラベルの対応候補。

### 5. 判断する（ここが人＝スキルの仕事）

#### どちらを主にするか

**カバー範囲が最も広いものを主にする。** `analyze` が推奨を出すが、鵜呑みにしない。
次の場合は推奨と違う方を選ぶ：

- 推奨された方の文字起こしが明らかに崩れている（同じ箇所を読み比べれば分かる）
- 推奨された方に録音中の欠落が多い（`analyze` の「録音中の無音」が頻発する）
- 録れている範囲はやや狭いが、発言者に近く音が良い方がある

迷ったら範囲の広い方。あとから欠落を埋める方が、崩れた本文を直すより楽。

#### 欠落をどう埋めるか

- **主録音のカバー範囲の外**（冒頭・末尾の録り逃し）→ 迷わず補完する。
  `--fill-outside <label>` でよい。
- **録音中の無音**（`inside`）→ 一律には埋めない。**本当に沈黙していたのか、
  片方の機器が拾えていなかったのか**を確かめる。他録音がその区間に発話を持っていて、
  かつ前後の文脈が途切れているなら、機器側の欠落なので `--fill` で埋める。
  休憩や資料を見ている時間なら埋めない。
- 補完区間は出力に `<!-- 補完区間（録音 B） ここから -->` が入る。消さない。
  **補完区間は別の機器の音声認識なので、文体も誤りの癖も主録音と違う。**

重複区間はどちらを採るか迷うが、**原則は主録音のまま通す。** 継ぎ接ぎを増やすと
どこがどの機器由来か分からなくなる。主録音の特定箇所が明らかに崩れている場合だけ、
その旨を注記して差し替える（本文を混ぜず、注記で「録音Bではこう」と併記する方が安全）。

#### 話者の同定

**話者ラベルは録音ごとに独立して振られる。A の Speaker 1 と B の Speaker 1 は別人。**
実例（2026-08-27）では6人全員が別番号だった：

| 録音B | 録音A |
|---|---|
| Speaker 1 | Speaker 3 |
| Speaker 2 | Speaker 1 |
| Speaker 3 | Speaker 4 |
| Speaker 4 | Speaker 5 |
| Speaker 5 | Speaker 2 |
| Speaker 6 | Speaker 6 |

`analyze` が発話時間の重なりから対応候補を出す。**重なり率が高い（8割以上）ものは
ほぼ信頼してよいが、短い発言が多い司会役は率が下がる**（上の例では議事進行役が41%だった）。
率が低いものは、本文を読んで裏を取る（「〇〇課長、お願いします」の直後に話し始めた人、など）。
対応が決まったら `--speaker-map "B/Speaker 1=A/Speaker 3"` で渡す。

表示名（`--name`）は**役職で書く。** 個人名は音声認識が崩すので、要約や文字起こしだけを
根拠に人名を書かない。裏が取れないものは `（推定）` を付ける。
1つのラベルに複数人が混ざっていることもある（診断のために本文を読むと分かる。
2026-08-27 では健康福祉課長と子ども家庭課長が同じラベルになっていた）。
その場合は名前にその旨を書いて、切り分けは人に任せる。

### 6. 組み立てる

```
python3 .claude/skills/report/scripts/merge_transcripts.py build \
    reports/verbatim/.work/rec_a.json reports/verbatim/.work/rec_b.json \
    --primary A --fill-outside B \
    --title "経済建設厚生常任委員会" \
    --suspect-terms .claude/skills/report/references/suspect-terms.json \
    --speaker-map "B/Speaker 1=A/Speaker 3" \
    --name "A/Speaker 3=建設課長（推定）" \
    -o "reports/verbatim/2026-08-27-経済建設厚生常任委員会.md"
```

保存先は `reports/verbatim/YYYY-MM-DD-<会議名>.md`。
既存ファイルがあれば上書きせず、差分を見せてどうするか聞く（日報・週報と同じ扱い）。

### 7. Word / テキストに変換する

議事録は Word で回覧・校正することが多い。**Word を求められたら必ず変換して渡す。**

```
python3 .claude/skills/report/scripts/verbatim_to_docx.py \
    "reports/verbatim/2026-08-27-経済建設厚生常任委員会.md"
```

同じ場所に `.docx` と `.txt` ができる（`--docx-only` / `--txt-only` で片方だけ）。
話者行・注記・表がそれぞれ段落として分かれるので、Word 上でそのまま直せる。

このスクリプトも標準ライブラリだけで動く（docx は XML を集めた ZIP なので、
この程度の構造なら pandoc も python-docx も要らない）。**`w:pPr` と `w:rPr` の
子要素は順序がスキーマで決まっている**ので、要素を足すときは順序に注意する
（`pStyle → pBdr → spacing → ind → jc`、`rFonts → b → color → sz`）。
順序を間違えると Word が「開けません」と言うだけで、原因が分からない。

### 8. 渡すときに伝えること

- これは校正前の土台であること
- 主録音はどれで、どこを別録音で補ったか
- ⚠ が何件あるか、「録音間で食い違った語」の表を先に見ると早いこと
- 1台しか録れていない区間は突き合わせによる検出が効かないこと

## 誤字の扱い

音声認識由来の誤字は逐語録にも残る。実例：

- 「崖崩れ」→ 録音Aでは「楽器崩れ」、録音Bでは「学級崩れ」（**どちらも誤り**）
- 「KDDI」→「KDTI」、「ホテイアオイ」→「ホテアウイアー」
- 「副村長」→「副産長」、「総合保健協会」→「総合保険協会」
- 村名そのものが「平田村」「平川村」「平賀村」「平岡村」と揺れる

**勝手に直さない。** スクリプトが3通りの印を付ける：

1. **語の食い違い** — 同じ時刻に、片方が「楽器崩」、もう片方が「学級崩」のように
   字面の近い別語を出している箇所。発言の下に併記される。
2. **片方にしかない語** — カタカナ語・英字・数字が一方にだけ出る箇所。
   金額の食い違い（21万7千円 / 121万7千円）はここで出る。
3. **辞書の語** — `references/suspect-terms.json` に登録した語。
   **1台しか録れていない区間で効くのはこれだけ。** 校正で実際に直した語は
   このファイルに足していく（誤って出てくる方の表記を書く）。

巻末に「要確認箇所の一覧」（時刻順）と「録音間で食い違った語」（語の対で集約）が付く。
**直すときは後者から見る。** 同じ誤りが何度も出るので、語ごとに1回判断すれば済む。

どちらが正しいかは音声を聴かないと決まらない。**両方とも誤りのことがある**
（上の「崖崩れ」がそれ）ので、片方を選べば済むとは考えない。

## よくある失敗

- **`transaction` や `outline` で取る** → 前者は読めない、後者は全文にならない。
  `transaction_polish` を使う。
- **`total` を確認せずページングを打ち切る** → 途中で切れた逐語録ができる。
  スクリプトが警告を出すので無視しない。
- **`start_time` をそのまま並べて2台をマージする** → 録音ごとに原点が違うので、
  時系列がぐちゃぐちゃになる。絶対時刻に直してから並べる。
- **話者ラベルを録音間で共通だと思う** → 別人の発言が同じ人にまとまる。
- **誤字を直してから渡す** → どこを直したか分からなくなる。印だけ付ける。
- **要約（`get_note`）で代用する** → 逐語録が要るのは要約では足りないからで、
  そもそもの目的を外している。
