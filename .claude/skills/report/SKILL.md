# 日報・週報ドラフト生成

対象期間の活動を各データソースから集め、**下書き**を作る。清書と送信は必ず人間がやる。

## このスキルが前提とする働き方

会議・打ち合わせが業務の中心。したがって**主軸は PLAUD の会議記録とカレンダー**で、報告書の価値は「何の会議に出たか」ではなく**「何が決まり、自分が何を引き受けたか」**にある。GitHub は補助的なソースで、開発作業がない期間は空でよい。

## 大原則

1. **送信しない。** メール送信、Slack投稿、ドキュメント共有は一切しない。成果物はローカルのMarkdownファイルのみ。ユーザーが明示的に「送って」と言った場合でも、まず下書きを見せて確認を取る。
2. **事実を作らない。** データソースに根拠がない作業を書かない。情報が薄い日は薄いまま出して、`> ⚠️ 自動収集できた情報が少ないです。補足してください。` を先頭に付ける。
3. **推測には印を付ける。** 会議名やコミットから意図を補完して書いた部分は `（推定）` を付けるか、末尾の「確認してほしい点」に列挙する。
4. **機微情報を持ち出さない。** 会議の文字起こしに含まれる評価・人事・給与・未公開の取引条件などは、報告書に転記しない。社外の個人名は原則イニシャルか役職表記にする。
5. **AI要約の固有名詞を鵜呑みにしない。** 自治体名・団体名・人名は要約段階で崩れることがある。要約だけを根拠に固有名詞を報告書へ書かない。
6. **話者が匿名なら自分のアクションを断定しない。** `[Speaker 1]` のような表記で本人が特定できない場合、アクションは会議全体の宿題として書き、切り分けが必要な旨を明記する。
7. **未実施の予定を実績にしない。** 実行時刻より後に始まる予定は「予定」として書き、`※作成時点では開始前` と明記する。

## 手順

### 1. 期間とモードを決める

- 引数に `日報` / `daily` → その日（指定がなければ今日）
- 引数に `週報` / `weekly` → その週の月曜〜金曜（指定がなければ直近の平日を含む週）
- `2026-08-25` のような日付、`先週`、`8/18-8/22` のような指定があればそれに従う
- 判断に迷ったら実行せずユーザーに聞く

期間を決めたら、まず一言で宣言する（例：`2026-08-24 〜 2026-08-28 の週報を作ります`）。
**現在時刻も必ず確認する**（`TZ=Asia/Tokyo date`）。当日分を作る場合、未実施の予定を切り分けるのに要る。

### 2. 設定を読む

リポジトリ直下の `report.config.json` を読む。無ければ `.claude/skills/report/config.example.json` の既定値で動き、初回は「設定ファイルを作りますか？」と提案する。

### 3. データを集める

`references/collection.md` の手順に従う。**PLAUD → カレンダー → GitHub の順**に集め、PLAUDとカレンダーは時刻で突き合わせて1件の会議にまとめる。

- 各ソースは**独立**なので、1つ落ちても他は続行する。落ちたソースは成果物の末尾に `（取得失敗: 〜）` として明記する。
- 収集結果は一度「活動ログ」（時刻・ソース・種別・要約・リンク）に正規化してから文章化する。この分離を崩さない — 収集ロジックだけ差し替えれば cron 常駐化に移せる形を保つ。

### 4. 文章化する

`references/templates.md` のテンプレートに沿って書く。

- **会議は「決まったこと」を書く。** 「〇〇会議に出席」だけでは価値がない。決定事項・自分のアクション・持ち越しの3点を拾う。文字起こしが無く中身が拾えない会議は、会議名と時刻だけ書いて `（内容未整理）` と付ける。
- 箇条書きは **1行1成果**。「〜を対応」ではなく「〜が原因の〜を修正し、〜が解消」まで書く。
- コミットメッセージをそのまま並べない。関連するコミット・PRをタスク単位にまとめる。
- 分量の目安：日報は本文 5〜15行、週報は 15〜30行。

### 5. 出力する

- 保存先：日報 `reports/daily/YYYY-MM-DD.md` / 週報 `reports/weekly/YYYY-Www.md`
- 既存ファイルがあれば**上書きせず**、差分を見せて追記・置換どちらにするか聞く。当日分の追記（午後の会議を後から足すなど）はよくあるケースなので、既存の内容は消さずに該当セクションへ差し込む。
- 保存後、本文をそのままターミナルにも表示する（ユーザーがコピペで使えるように）。
- 最後に「確認してほしい点」を3つ以内で挙げる（推定した箇所、情報が取れなかった箇所、書くか迷った機微情報）。

### Google Drive への保存

`output.drive.enabled` が true なら、ローカル保存に加えて Drive にも保存する。スマホから読むための出力先。

- 保存先フォルダは `output.drive.folderId`
- タイトルは `日報 2026-08-28（金）` / `週報 2026-08-24 〜 2026-08-28` の形。**日付を含めて一意にする**
- `create_file` に `contentMimeType: "text/markdown"` を渡す。Google ドキュメントへ自動変換され、見出しと箇条書きが書式として反映される（`disableConversionToGoogleType` は指定しない）

**既にある日の分を作り直すとき**（速報を確定版に差し替える場合など）:

`update_file` は**タイトルと保存場所しか変えられず、本文を上書きできない**。そのため次の順で行う。

1. `search_files` で `parentId = '<folderId>' and title = '<同じタイトル>'` を検索
2. 見つかったら、**内容に変化があるときだけ** 古いファイルを `trash_file` し、新しい内容で `create_file` する
3. 内容が変わらないなら何もしない（毎回URLが変わるのを避けるため）

Drive のURLは毎回変わりうるので、報告書本文にDriveリンクを埋め込まない。

## 逐語録を作る（別の成果物）

議会の委員会など、**要約ではなく全文の議事録が要る**場合に使う。
「逐語録」「全文」「一言一句」「議事録を起こして」と言われたらこちら。日報・週報とは別物。

- 手順とスクリプトの使い方：`references/verbatim.md`
- 2台のデバイスで録った同じ会議は1本にまとめる。**単純な結合ではない** —
  片方が冒頭を録り逃していることがあるので、カバー範囲の広い方を主とし、欠落を補う
- 出力：`reports/verbatim/YYYY-MM-DD-<会議名>.md`（`.gitignore` 済み。Drive には上げない）
- **音声認識の誤字は直さない。印を付けて人に渡す。** 固有名詞・数字は必ず崩れる

日報・週報のために逐語録を作る必要はない。日報は要約（`get_note`）で足りる。

## よくある失敗

- **カレンダーの予定を全部書く** → 定例の朝会や移動時間は成果ではない。`calendar.excludePatterns` で落とす。
- **参加者が空の予定を捨てる** → 自分で登録した予定は参加者リストが空になる。これは「自分だけの予定」ではない。既定では捨てない（`excludeSoloEvents: false`）。
- **同じ予定を重複して書く** → 同一時刻・同一タイトルの予定が複数登録されていることがある。必ず名寄せする。
- **PLAUDの文字起こし全文を読み込む** → コンテキストを食い潰す。まず要約（note）を取り、足りないときだけ該当箇所の transcript を取る。
- **PLAUDをアップロード日で拾う** → 前日の会議が翌日アップされる。必ず**録音日**（`start_at`、UTC）で判定する。
- **未実施の会議を実績に書く** → 実行時刻を確認し、これからの予定と切り分ける。
- **週報を日報の連結にする** → 週報は「進捗と見通し」。日単位の羅列ではなくテーマ単位でまとめる。
