# 日報・週報ドラフト生成

対象期間の活動を各データソースから集め、**下書き**を作る。清書と送信は必ず人間がやる。

## 大原則

1. **送信しない。** メール送信、Slack投稿、ドキュメント共有は一切しない。成果物はローカルのMarkdownファイルのみ。ユーザーが明示的に「送って」と言った場合でも、まず下書きを見せて確認を取る。
2. **事実を作らない。** データソースに根拠がない作業を書かない。情報が薄い日は薄いまま出して、`> ⚠️ 自動収集できた情報が少ないです。補足してください。` を先頭に付ける。
3. **推測には印を付ける。** コミットや予定から意図を補完して書いた部分は `（推定）` を付けるか、末尾の「確認してほしい点」に列挙する。
4. **機微情報を持ち出さない。** 会議の文字起こしに含まれる評価・人事・給与・未公開の取引条件などは、報告書に転記しない。社外の個人名は原則イニシャルか役職表記にする。

## 手順

### 1. 期間とモードを決める

- 引数に `日報` / `daily` → その日（指定がなければ今日）
- 引数に `週報` / `weekly` → その週の月曜〜金曜（指定がなければ直近の平日を含む週）
- `2026-08-25` のような日付、`先週`、`8/18-8/22` のような指定があればそれに従う
- 判断に迷ったら実行せずユーザーに聞く

期間を決めたら、まず一言で宣言する（例：`2026-08-24 〜 2026-08-28 の週報を作ります`）。

### 2. 設定を読む

リポジトリ直下の `report.config.json` があれば読む。無ければ `.claude/skills/report/config.example.json` の既定値で動き、初回は「設定ファイルを作りますか？」と提案する。設定項目の意味は同ファイルのコメント参照。

### 3. データを集める

`references/collection.md` の手順に従って、設定で有効になっているソースだけを叩く。

- 各ソースは**独立**なので、1つ落ちても他は続行する。落ちたソースは成果物の末尾に `（取得失敗: 〜）` として明記する。
- 収集結果は一度「活動ログ」（時刻・ソース・種別・要約・リンク）に正規化してから文章化する。この分離を崩さない — 収集ロジックだけ差し替えれば cron 常駐化に移せる形を保つ。

### 4. 文章化する

`references/templates.md` のテンプレートに沿って書く。

- 箇条書きは **1行1成果**。「〜を対応」ではなく「〜が原因の〜を修正し、〜が解消」まで書く。
- コミットメッセージをそのまま並べない。関連するコミット・PR・会議をタスク単位にまとめ、読み手（上司・チーム）が意味を取れる粒度にする。
- 会議は「出た」ではなく「何が決まったか」を書く。決定事項が拾えなければ会議名だけ書いて `（内容未整理）` と付ける。
- 分量の目安：日報は本文 5〜10行、週報は 15〜30行。超えるなら粒度が細かすぎる。

### 5. 出力する

- 保存先：日報 `reports/daily/YYYY-MM-DD.md` / 週報 `reports/weekly/YYYY-Www.md`
- 既存ファイルがあれば**上書きせず**、差分を見せて追記・置換どちらにするか聞く。
- 保存後、本文をそのままターミナルにも表示する（ユーザーがコピペで使えるように）。
- 最後に「確認してほしい点」を3つ以内で挙げる（推定した箇所、情報が取れなかった箇所、書くか迷った機微情報）。

## よくある失敗

- **カレンダーの予定を全部書く** → 定例の朝会や移動時間は成果ではない。設定の `calendar.excludePatterns` で落とす。
- **PLAUDの文字起こし全文を読み込む** → コンテキストを食い潰す。まず要約（note）を取り、足りないときだけ該当箇所の transcript を取る。
- **他人のコミットを自分の成果に書く** → GitHub は必ず author を自分に絞る。
- **週報を日報の連結にする** → 週報は「進捗と見通し」。日単位の羅列ではなくテーマ単位でまとめる。
