# 議会だより かんたん原稿ツール 設計書

版 1.1／2026-09-22 更新（校正・文字数チェック・LLM 差し込み口を追加）

この文書は「このツールが何を、どういう考えで、どう動かしているか」を、次の担当者や
手直しする人が読めるようにまとめたものです。使い方だけを知りたい場合は `README.md` を
読んでください。

---

## 1. 目的と割り切り

### 解決したい困りごと

議会だよりは、年 4 回（3・6・9・12 月定例会のあと）、次の作業を繰り返して作ります。

1. 議員や事務局から届いた原稿（Word・テキスト）を紙面の順に並べる
2. 写真を集め、「どの記事のそばに、どの大きさで」置くかを決める
3. 文字だけの原稿 Word・写真・配置の指示を印刷所に渡す（組版は印刷所が行う）

このツールは **1 と 2 を誰でも同じ手順でできるようにし、3 の渡すものを 1 回の操作で作る**
ことだけを目的にしています。

### やらないこと（意図的に外したもの）

| やらないこと | 理由 |
|---|---|
| 原稿の自動解析（見出し・区分・議員名の推測） | 書き方が少し変わるたびに直す必要が出て、引き継げなくなる |
| 要約（字数を削る） | 何を残すかは人が決める。分量は「分量を見る」で示すところまで |
| 議案・賛否表の自動転記 | 賛否表は Excel を「別添」に入れて印刷所に渡すだけで足りる |
| 名簿・委員会名の管理 | 改選のたびにコードを直すことになる |
| 紙面の組版（段落ち・写真枠の再現） | 組版は印刷所の仕事。原稿 Word は「指示が伝わる形」であればよい |
| 通信 | 原稿・写真・議員名を外部に出さない。すべてこのパソコンの中で完結する |

**推測をしない**のが一貫した方針です。書いてあるとおりに並べ、書いてあるとおりに写真を置きます。

## 2. 全体の流れ

```
 利用者                         ツール                                出力
 ──────                         ────────                              ────
 号を作る（号数・発行日・種類） ─▶ 第○号/ フォルダと区分ファイルを生成
 区分を選んで原稿を書く／      ─▶ 01_表紙.txt … NN_区分.txt に保存
   取り込む（.docx/.doc/.txt）      （取り込み時に数字をそろえる）
 写真を「写真」フォルダへ      ─▶ サムネイル一覧に表示、使用済みを色分け
 写真を選んで「入れる」        ─▶ 原稿に 【写真】ファイル名｜大きさ｜説明 の 1 行
 「Word を作る」               ─▶ 原稿 Word（表紙横書き・本文縦書き 5 段、    ─▶ 出力/第○号_原稿.docx
                                    写真入り・縦中横）                          出力/第○号_写真配置指示.docx
                                    写真配置指示書（一覧表・別添の一覧）
```

印刷所に渡すもの: `出力/` の Word 2 つ、`写真/` の中身、`別添/` の中身。

## 3. データの持ち方

### 3.1 号フォルダ（1 号 = 1 フォルダ）

```
第204号/
  号情報.json                  {"gou": "204", "hakkoubi": "令和８年７月31日", "template": "6月号"}
  01_表紙.txt                  区分ファイル。番号の順 = 紙面の順
  02_行政報告.txt
  …
  写真/                        写真の原本。ツールは読むだけで書き換えない
  別添/                        賛否一覧表の Excel など
  出力/                        生成した Word
  はじめにお読みください.txt   フォルダの使い方（人向け）
```

設計上のねらい:

- **ファイルがそのまま設計** — 区分の一覧はどこにも別管理しない。フォルダに `NN_名前.txt` があれば、それが区分。
  メモ帳で足しても、ツールで足しても同じ。
- **引き継ぎはフォルダのコピー** — 作業データはこのフォルダの外にない（ツールの設定ファイルは「最後に開いたフォルダ」を覚えているだけ）。
- テキストは **BOM 付き UTF-8** で書く。Windows のメモ帳で開いても文字化けしない。
  読むときは UTF-8 → CP932 → EUC-JP の順に試す（議員から届いた Shift-JIS のテキストも読める）。

### 3.2 【写真】行の文法

```
【写真】ファイル名｜大きさ｜説明
```

| 部分 | 規則 |
|---|---|
| 先頭 | 行頭（空白可）に `【写真】` |
| ファイル名 | `写真/` の中のファイル名。区切り文字（｜ または \|）を含まない任意の文字列 |
| 大きさ | `表紙` `大` `中` `小` `顔` のどれか。省略すると `中` |
| 説明 | 任意。省略可 |

対応する正規表現は `core.PHOTO_LINE`。`大きさ` を空にして説明だけ書く（`【写真】x.jpg｜｜説明`）ことも許す。

大きさは **印刷所への幅の指示**（`core.SIZES`）:

| 大きさ | 幅 | 目安 |
|---|---|---|
| 表紙 | 210mm | A4 一面（紙の端まで）。表紙の区分でだけ使う。Word には余白内 170mm で貼る |
| 大 | 80mm | 3 段弱 |
| 中 | 55mm | 2 段 |
| 小 | 38mm | 1 段と少し |
| 顔 | 26mm | 議員・委員長の顔写真 |

（紙面は 5 段組、1 段の幅は約 30mm。）

### 3.3 号の種類と区分の雛形

第198〜201号（1 年分）を読んで確認した構成を `core.TEMPLATES` に持っています。

| 号の種類 | 区分（紙面の順） |
|---|---|
| 3月号 | 表紙 → 行政報告 → 審議したこと・決まったこと → **当初予算の概要** → 閉会中の委員会活動報告 → 一般質問 → 特集 → 裏表紙 |
| 6月号 | 表紙 → 行政報告 → 審議したこと・決まったこと → 閉会中の委員会活動報告 → 一般質問 → 特集 → 裏表紙 → お知らせ |
| 9月号 | 表紙 → 行政報告 → 審議したこと・決まったこと → **決算の概要** → 閉会中の委員会活動報告 → 一般質問 → 特集 → 裏表紙 → **議員行政視察研修報告** → お知らせ |
| 12月号 | 表紙 → 行政報告 → 審議したこと・決まったこと → 閉会中の委員会活動報告 → 一般質問 → 特集 → 裏表紙 → **行政視察・研修報告** → お知らせ |

雛形は「号を作るときの初期状態」にすぎません。作ったあとは自由に足し引きできます。
`core.HINTS` に区分ごとの「載せるもの（前年の例）」を持ち、画面に表示します。

`表紙` という名前の区分だけ特別扱い（横書き、数字を変換しない）。`core.COVER` で名前を決めています。

## 4. 画面（`app.pyw`）

Tkinter（Python 標準）で 1 画面。ブラウザやサーバーは使いません。

```
┌ [新しい号を作る] [号フォルダを開く]  第204号（6月号） 発行日 …   [使い方] ┐
│ 区分（紙面の順）│ ■ 行政報告            [取り込む][数字をそろえる][保存] │ 写真 [読み直す][写真フォルダ] │
│ 表紙 96字・写真0│ 載せるもの: 村長の…（ヒント）                         │ ┌──┐┌──┐┌──┐            │
│ 行政報告 …     │ ┌──────────────────────────────────┐ │ │  ││  ││  │ サムネイル │
│ 審議したこと … │ │ 原稿（tk.Text）                                  │ │ └──┘└──┘└──┘            │
│ …             │ │                                                  │ │ 緑=使用済み 青=選択中     │
│ [▲][▼][追加][外す]│ └──────────────────────────────────┘ │ 大きさ[中▾] 説明[      ]   │
│                │                                                    │ [カーソル位置に入れる]     │
├ [Word を作る] [出力フォルダを開く] [別添フォルダを開く]   状態表示 ──────────────────────────┤
```

### 主な動き

| 操作 | 処理（メソッド） | 補足 |
|---|---|---|
| 新しい号を作る | `NewIssueDialog` → `core.Issue.create` | 号数・発行日・種類を 1 つのダイアログで。フォルダの場所は OS の選択画面 |
| 号フォルダを開く | `open_issue` | 設定ファイル `~/.gikai_simple.json` に最後の場所を記録。次回起動時に自動で開く |
| 区分を選ぶ | `on_select_kubun` | 切り替え前に `save_current` で自動保存。ヒントと字数を表示 |
| 一つ手前に戻す | `undo` / `redo` / `update_undo_buttons` | `tk.Text` の undo を使う。**全文を入れ替える操作（`replace_text`）は `autoseparators` を一時的に切って 1 つの区切りにまとめる**ので、一括修正も 1 回で戻る。区分を切り替えると `edit_reset()` で履歴を捨てる（別の区分の履歴が混ざらないように） |
| 文字を選ぶ | `update_count`（`<<Selection>>` などで発火） | 選んだ範囲（無ければ区分ぜんぶ）の字数を出す。見たままの字数と組版の幅の両方。紙面の大きさに応じて 行→段→ページ と単位を変える |
| 区分の追加／▲▼／外す | `add_kubun` / `move_kubun` / `remove_kubun` | ファイルの番号を付け直す。外せるのは空の区分だけ（確認ダイアログあり） |
| 号の情報を変える | `edit_issue` → `set_info` / `template_diff` / `add_missing_kubun` / `rename_folder` | 作ったあとから号数・発行日・種類を直す。種類を変えたら足りない区分を足すか、号数を変えたらフォルダ名も変えるかを、それぞれ確認してから行う。**原稿は消さず、余分な区分も残す**（表紙に書いた号数は自動で直さない） |
| 原稿を取り込む（カーソル位置） | `import_files` → `core.import_manuscript` | 文字だけ**カーソル位置**に差し込む。行の途中なら前後に改行を足して独立した段落にする。複数選んでも取り消しは 1 回。数字もそろえる |
| 数字をそろえる | `fix_numbers` → `core.normalize_numbers` | 今開いている区分だけ |
| 写真を選ぶ | `select_photo` | 画素数と「350dpi で何 mm 幅まで使えるか」を表示 |
| カーソル位置に入れる | `insert_photo` | 空行ならその行に、文字のある行ならその次の行に【写真】行を挿入。解像度不足なら確認 |
| Word を作る | `build` → `core.build_all` | 保存 → 生成 → 注意事項の一覧を表示 → 原稿 Word を開くか聞く |

保存のタイミングは「区分を切り替えたとき」「取り込み・挿入・数字そろえのあと」「Word を作るとき」「閉じるとき」。
`tk.Text` の `edit_modified` フラグで変更の有無を見て、変更がなければ書きません。

### 画面が担っていないこと

判断や変換のロジックは画面側に置いていません。画面は `core.py` を呼ぶだけです。
そのため `core.py` は画面なしでテストでき（`tests/test_core.py`）、画面は薄く保てます。

## 5. 中核（`core.py`）

### 5.1 モジュールの地図

| 区画 | 主な関数・クラス | 役割 |
|---|---|---|
| 決まりごと | `TEMPLATES` `HINTS` `SIZES` `MARGIN_MM` など | 変えたくなる値をすべて先頭の定数に集める |
| 原稿の解釈 | `parse_photo_line` `parse_blocks` `photo_refs` `count_chars` | 原稿を「本文」と「【写真】行」に分ける |
| 数字の表記 | `normalize_numbers` `to_zenkaku_digits` | 縦書きの慣行に合わせる（§6） |
| 号フォルダ | `Issue`（`create` `open` `kubun_list` `add_kubun` `move_kubun` `remove_kubun` `read_text` `write_text` `photo_files` `photo_usage` `all_refs` `attach_files`） | フォルダの読み書き |
| 取り込み | `read_text_file` `import_manuscript` `docx_to_text` + `doc97.extract_text` | 文字コードの判別、Word からの文字取り出し |
| 写真の情報 | `photo_info` `PhotoInfo.warning_for` `reduced_jpeg` | 画素数・解像度判定・貼り付け用の縮小 |
| Word 生成 | `build_manuscript` `build_photo_sheet` `build_all` と `_para` `_setup_page` `_add_body_section` `_add_photo` | §7 |

### 5.2 原稿の解釈

`parse_blocks(text)` は行ごとに `parse_photo_line` を試し、
`("text", 連続する本文)` と `("photo", PhotoRef)` の並びに分けます。空行は本文の一部としてそのまま残します。
`count_chars` は【写真】行と空白を除いた字数（画面の「○字」表示用）。

### 5.3 区分ファイルの番号付け直し（`Issue._renumber`）

追加・移動・削除のたびに `01_ 02_ …` を付け直します。番号の衝突を避けるため、
いったん `~NN_名前.txt` に退避してから本来の名前に戻す 2 段階で行います。中身は触りません。

### 5.4 取り込み

| 形式 | 方法 |
|---|---|
| `.docx` | `document.xml` を直接読み、段落ごとに文字を連結。テキストボックス（`txbxContent`）の中も拾う。`<!DOCTYPE` や `<!ENTITY` を含む XML は「通常の Word ではない」として拒否（XML 爆弾対策） |
| `.doc` | `doc97.py`（`gikai_editor` から複製。標準ライブラリだけで Word 97-2003 形式を読む） |
| `.txt` | 文字コード自動判別 |

書式はすべて捨て、段落の区切りだけ改行として残します。

## 6. 数字の全角・半角（縦書きの慣行）

第198〜201号の `.doc` を集計して確認した規則を `normalize_numbers` に実装しています。

| 規則 | 例 |
|---|---|
| 1 桁は全角 | ４人、３月、第８号 |
| 2 桁以上は半角 | 第46回、国道33号、131チーム、2025年 |
| 「－」でつないだ番号はそのまま | 〒７８１－２１９４、℡０８８９－２４－７７７７、本郷６１－１ |
| 表紙と【写真】行は触らない | 題字の「第２０４号」、写真のファイル名 |

適用する場面は 3 つ: 取り込み時、「数字をそろえる」ボタン、Word 生成時（表紙以外）。
Word 生成時に掛けるので、手で書いた文章でも出力は必ずそろいます（原稿ファイルは書き換えません）。

さらに Word 上では、2〜3 桁の半角数字に **縦中横**（`<w:eastAsianLayout w:combine="1"/>`）を掛け、
縦書きでも数字が横に寝ないようにします（`_para(..., tatechuyoko=True)`）。4 桁以上はそのままです。

決めきれなかった点: 西暦 4 桁は従来の原稿でも「2025」「２０２５」が混在していました。規則どおり半角にしています。

## 6-2. 校正と文字数チェック

### なぜ 2 段構えか

誤りには **規則で決まるもの** と **文脈で決まるもの** があり、向いている道具が違います。

| | 規則で決まる | 文脈で決まる |
|---|---|---|
| 例 | 等→など、ら抜き、括弧の不対応、山崎→山﨑 | 脱字、以外／意外、係り受けの乱れ |
| 担当 | `proofread.py`（ルールベース） | `llm.py`（ローカル LLM・任意） |
| 確実さ | 高い。自動修正してよい | 低い。人が見て判断する |
| 動く条件 | どのパソコンでも | Ollama とモデルが入っているパソコンだけ |

**土台はルールベース**で、LLM は差し込み式です。LLM が無くても機能が欠けるだけで壊れません。
役場のパソコンはインターネットにつながらないため、LLM は「入れられたら使う」位置づけにしています。

### `proofread.py`（ルールベース校正）

`gikai_editor/gikai/proofread.py` を複製し、`textutil` に依存していた 4 関数
（`is_fullwidth` `count_chars` `split_sentences` `levenshtein`）を中に取り込んで、
このフォルダだけで動くようにしたものです（`doc97.py` と同じ考え方）。

指摘は `Issue`（位置・該当文字列・種類・重要度・説明・直し方・自動修正可か）で返します。
重要度は `error`（要修正）／`warn`（確認）／`info`（参考）。

辞書は `proof_data/` の 4 つ。**コードを直さずに辞書だけ直せる**のが要点で、
議員の改選や新しい施設名にはここで対応します。

| ファイル | 中身 |
|---|---|
| `style_rules.json` | 表記ルール 73（house 6・kana 30・redundant 19・keigo 7・symbols 11） |
| `confusions.json` | 同音異義語 43 組、誤字 14 |
| `local_terms.json` | 日高村の固有名詞 109 語（地名31・施設13・役職者12・議員10・組織19・事業24）と、取り違えやすい漢字 20 組 |
| `ruby.json` | 難読語 59 語 |

`apply_fixes` は **後ろから置換**して位置ずれを防ぎ、重なる指摘は前のものを優先します。
`auto_fixable` が真で `suggestion` があるものだけが対象なので、
「まず最初に → まず／最初に」のようにどちらか選ぶものは自動修正されません。

### 文字数チェック（`core.py`）

紙面に入る量を計算します。縦書き 5 段では、文字は**段の高さの向き**に並び、
行は**紙の横幅の向き**に進みます。

```
1 行の字数 = 段の高さ 49.2mm ÷ 文字の大きさ 3.88mm = 12 字
1 段の行数 = 本文の横幅 180mm ÷ 行送り 4.93mm     = 36 行
1 ページ   = 12 × 36 × 5 段                      = 2160 字
```

（ＭＳ ゴシック 11pt・行間 1 行での値。行送りは字の大きさの約 1.27 倍で、Mac の Word で
第201号を測った値。`page_capacity()` が設定から計算します。第198〜201号の 1 段 12 字と同じ。）

- `count_width()` — 組版の幅で数える（半角は 0.5 文字）。`count_chars()`（素の字数・画面の「○字」用）とは別物
- `photo_chars()` — 写真が本文を押しのける量。写真の面積 ÷ 1 文字の面積（19.1mm²）＋ 指示文とキャプションの行
- `Issue.estimate()` — 区分ごとの字数・写真ぶん・ページ数と、全体のページ数。
  表紙は横書きで組み方が違うので計算から外し、1 ページとして数えます。
  **奇数ページなら知らせます**（紙は表と裏があるので最後が白紙になる）

### `llm.py`（ローカル LLM の差し込み口）

Ollama の HTTP API（`/api/tags` と `/api/generate`）を標準ライブラリだけで叩きます。

**外に出さないための作り:**

- つなぐ先は `ALLOWED_HOSTS = ("127.0.0.1", "localhost", "::1")` のみ。
  `_check_host()` がそれ以外を例外で弾くので、**設定で外部のサービスを指すことはできません**
- 追加の部品（requests など）を使わない。持ち込む物を増やさないため

**小さいモデルでも使えるようにする工夫:**

| 工夫 | 理由 |
|---|---|
| 400 字ずつ、文の切れ目で区切って渡す | 長い文章を渡すと小型モデルは精度が落ちる |
| `temperature: 0` | 同じ原稿には同じ答えが返るように |
| 指示文で「確信のあるものだけ」と念を押す | 誤検出のほうが実害が大きい |
| 返事から `[...]` を正規表現で拾う | 小型モデルは前置きを付けて JSON を崩しがち |
| 本文に実在する文字列だけ採用する | モデルが原文にない語を返すことがある |
| 重要度は必ず `info`、`auto_fixable` は常に偽 | 人の確認を必ず挟ませる |
| 失敗したかたまりは黙って飛ばす | 一部でも結果が出たほうが役に立つ |

画面では別の流れ（スレッド）で動かし、進み具合を出します（CPU だけだと数分かかるため）。

### 実際に試した結果（2026-09-22・メモリ 8GB の Mac）

第201号の刷り上がった原稿 1,200 字（＝誤りが無いはずの文章）と、わざと 3 つ誤りを入れた
文章で測りました。

| モデル | 誤検出 | 検出 | 速さ |
|---|---|---|---|
| `qwen2.5:3b` | 3 件 | 0/3 | 23 字/秒 |
| `qwen2.5:7b` | 0〜2 件 | 1/3 | 19 字/秒 |

3b は「武政義幸様 → 武政義幸様」のように**直っていない指摘**や、固有名詞の書き換え、
文まるごとの言い換えを返してきました。これを受けて `_is_noise()` のふるいを入れ、
9 件あった誤検出を 3 件まで減らしています。それでも 3b は本当の誤りを 1 つも拾えなかったため、
`PREFERRED` で **7b を優先**するようにしました。

**この機能への評価:** 7b でも 3 つのうち 1 つしか拾えず、同じ原稿でも実行のたびに結果が
変わります。**ルールベース校正の置き換えにはならず、補助にとどまります。**
そのため指摘は必ず `info`（参考）で出し、自動修正の対象から外しています。

## 7. Word の生成

python-docx で作ります。テンプレート Word は使わず、白紙から組み立てます。

### 7.1 原稿 Word（`build_manuscript`）

| 項目 | 内容 |
|---|---|
| 用紙 | A4 縦 |
| セクション 1（表紙） | 横書き 1 段、余白 20mm。冒頭に「ひだか議会だより 第○号 原稿」「発行日／作成日」「赤字の注意書き」 |
| セクション 2（本文） | **縦書き**（`textDirection=tbRl`）**5 段**（`cols num=5 space=340twip≒6mm`）、余白 上15・下12・左右15mm。第203号の紙面の実測値 |
| 本文 | ＭＳ明朝 10.5pt、行送り 1.45。区分ごとに「■ 区分名」（ＭＳゴシック 14pt）＋改ページ |
| 写真 | 【写真】行の位置に赤字の指示文「【写真n】ファイル名（大きさ・幅○mm）　説明: …」＋縮小した写真。写真は 1 段の高さ（`DAN_HEIGHT_MM` ≒ 49mm）に収まるよう縮める。**幅の指示は赤字のまま**（印刷所向け） |
| 注意 | 写真が無い・解像度不足・原稿が空 の区分は赤字で書き、戻り値の `warnings` にも入れる |

`textDirection` は `sectPr` の中で `docGrid` より前に置く必要があります（順番を誤ると Word が開けない）。

### 7.2 写真配置指示書（`build_photo_sheet`）

横書きの表: 番号（原稿 Word の【写真n】と同じ）・縮小画像・ファイル名と画素数・区分・大きさ・説明・解像度の注意。
末尾に「原稿で使っていない写真」と「別添フォルダの中身」を列挙します。

### 7.3 写真の扱い

- 原本は読むだけ。貼るときは Pillow で EXIF の向きを直し、最大 1200px の JPEG をメモリ上に作って埋め込む（Word が重くならない）
- 解像度判定: `幅px / 350dpi × 25.4` が指示の幅（mm）に足りなければ「解像度不足」
- Pillow が無い環境でも動く（縮小・向き補正・判定ができないだけ）

## 9. 動作環境と既知の制約

| 項目 | 内容 |
|---|---|
| Python | 3.9 以降（Windows 想定。`起動.bat` は `py` → `pythonw` の順に探す） |
| 追加部品 | python-docx（必須: Word を作る）、Pillow（推奨） |
| macOS | 付属 Python の Tk 8.5 は描画不良で画面がほぼ白紙になる。python.org の Python 3.12 以降を使う |
| HEIC | Pillow 単体では読めない。「読み込めません」と出るので JPEG に変換して入れる |
| 4 桁以上の数字 | 縦中横を掛けない（横に寝る）。必要なら `_TATECHUYOKO` の桁数を変える |
| 賛否一覧表 | Excel を「別添」に入れるだけ。中身は読まない |
| AI 校正 | Ollama とモデル（1〜2GB）が要る。CPU だけだと 1 区分で数分。小型モデルは誤検出が多い |
| 校正の辞書 | 議員名などは改選のたびに `proof_data/local_terms.json` を直す |
