# メール作成用QRコード／オフライン版　設計図

最終更新: 2026-10-01

---

## 1. このツールは何か

スマホで読み取ると、**宛先・件名・本文があらかじめ入力された状態でメールソフトが開く**QRコードを作るツール。
参考にしたのは Web サービス「メール作成用QRコード（qr.quel.jp）」。それを**完全オフラインで動く Windows 用ツール**として作り直したもの。

- **形式**: HTML ファイル1つ（`QRメール作成ツール.html`）。ダブルクリックで Edge 等のブラウザが開き、そのまま動く。
- **インストール不要・ネット接続不要**。QRコードの生成処理をすべてファイル内に自前実装しており、外部サーバーや CDN へ一切アクセスしない。
- **入力した内容がパソコンの外へ出ることはない**（[個人情報の外部送信絶対禁止] の方針に適合）。

### なぜ自作したか
既存の Web サービスは、入力した宛先・本文が外部サーバーへ送られる。役場の受付用QR（道路破損通報など）には使えない。庁内ネットワークから切り離した PC でも職員が自分で作れる必要があった。

## 3. 画面の機能

### 入力
- **宛先アドレス**（必須）
- **件名**
- **本文**（記入フォームのひな形を入れる想定）

### QRコードの設定
- **誤り訂正レベル** L / M / Q / H（既定 M）
- **貼り付け・印刷する大きさ**（実寸 mm。15〜120mm）
- **日本語の入れ方** compact（そのまま）／ safe（記号に変換）＝第7章参照

### 出力
- **画像をコピー**（Word/Excel へ Ctrl+V）
- **PNG画像で保存**
- **SVGで保存**
- **印刷**
- 「QRコードに実際に入る文字列」の確認欄とコピー

### 定型文（第6章）
- 宛先・件名・本文＋設定をまとめて保存／呼び出し／編集／並べ替え／削除
- JSON ファイルへ書き出し・読み込み

## 4. QRコードエンジン（技術仕様）

- 規格 **ISO/IEC 18004**、**8ビットバイトモード**専用。バージョン1〜40、誤り訂正 L/M/Q/H、マスク0〜7 すべて対応。
- `mailto:` の中身は（日本語をそのまま入れる場合も）数字モード最適化や漢字モード・ECI は使わず、バイトモードのみ。
- 誤り訂正の RS ブロック表・位置合わせパターン表は、規格表を手打ちすると必ず誤るため、Python ライブラリ `qrcode` から機械的に書き出して埋め込んだ。

### 検証の裏付け（重要）
自作エンジンは「見た目はQRだが読めない」ものを生みやすいため、二重に検証済み。

1. **基準実装との完全一致**: 40バージョン × 4レベル × 8マスク × 2データ長 ＝ **2,560通り**を生成し、Python `qrcode` とビット単位で照合 → **不一致ゼロ**。
2. **実デコード**: 生成したQRを画像化し OpenCV の QRデコーダで読み取り → 日本語・最大級サイズ含めすべて成功。
3. 画面のキャンバスに描いた実ピクセルも、1マスずつ色を照合して不一致ゼロを確認。

## 5. 「できないこと」と、その理由（蒸し返さないための記録）

### 写真などファイルの自動添付は不可能
- QRに入れるのは `mailto:宛先?subject=…&body=…` という文字列。この書式（RFC 6068）が扱えるのは**宛先・件名・本文・CC・BCC だけ**で、添付ファイルの項目が存在しない。
- 過去に一部メールソフトが独自対応した `attach=` は、「QRを読ませるだけで相手PC内のファイルを勝手に送信させる」攻撃に悪用できるため、Outlook・Gmail・iPhone標準メール等が現在すべて塞いでいる。
- そもそもQRの容量は最大 約2,953バイト。写真1枚（2〜5MB）は1000倍以上入らない（規格上の物理的上限）。

### 代替運用
本文テンプレに「※このメールに画像を添付してください」と書いておき、相手のメールソフトで添付してもらう。組み込み定型文「画像添付の受付」がこの文面。

### 画面上の表示について
「写真の添付について」の解説ブロックは、職員から「不要」との判断で削除済み（定型文そのものは残置）。

## 6. 定型文の仕組み

### 保存方式は JSON ファイル（localStorage は意図的に不採用）
- **なぜ localStorage を使わないか**: ブラウザ内保存だと定型文が「そのPCのそのブラウザ」にしか存在せず、担当者交代や Edge の「閲覧データの削除」で消える。消えた理由も分かりにくい。
- **JSON ファイル方式**なら、共有フォルダに置いて全員で同じ定型文を使え、引き継ぎもバックアップも通常の書類と同じ。外部送信は発生しない。
- 「定型文を書き出す」→ `QRメール定型文.json`、「定型文を読み込む」で復元。書き出していない変更があると画面に「未書き出しの変更があります」と出し、離脱時にブラウザが確認する。

### 定型文が記憶する項目
名前・宛先・件名・本文に加え、**誤り訂正レベル・大きさ(mm)・日本語の入れ方**も記憶する。
→「25mm角に収まる設定」がボタン一発で完全再現され、設定戻し忘れで読めないQRを作る事故を防ぐ。

### 定型文の適用ルール
呼び出したとき、**その定型文で空の項目は、いま入力中の内容をそのまま残す**（宛先・件名・本文とも）。本文を消すのは専用の「本文を消す」ボタン。

### JSON のバージョン互換
- 現行は `version: 3`（`ecl`・`mm`・`enc` を含む）。
- `version: 1`（宛先・件名・本文のみ）、`version: 2`（＋ecl・mm）の旧ファイルもそのまま読める。
- 不正な値（存在しない ecl/mm/enc など）は黙って捨て、残りは正常に読み込む。壊れたJSONや別形式は、日本語メッセージを出して現在の定型文を壊さずに中止する。

### 組み込み定型文（初期状態）
1. 画像添付の受付（25mm角）: `【お名前】/【ご連絡先】/※このメールに画像を添付してください。` ・M・25mm・compact
2. 写真を添付してもらう受付: フル項目・M・40mm・compact
3. 参加申込の受付: M・40mm・compact
「初期状態に戻す」でいつでも復元可。

## 7. 日本語の入れ方（QRの大きさを左右する最重要ポイント）

同じ文面でも、日本語の表し方で情報量が**3倍**変わる。

| 方式 | 日本語1文字 | 特徴 |
|---|---|---|
| **compact（既定・推奨）** | 3バイト | 日本語をそのまま埋める。QRが小さい。 |
| **safe（互換重視）** | 9バイト（`%E5%90%8D` 形式） | 全部パーセントエンコード。どの読取アプリでも確実だがQRが大きい。 |

### compact の安全対策
日本語を生で入れつつ、**改行・空白・`& ? # %` などURL構造を壊す文字だけはパーセントエンコード**する。
実装は、`encodeURIComponent` の出力のうち UTF-8 多バイト列だけを元に戻す方式（正規表現 `(?:%[CDEF][0-9A-F](?:%[89AB][0-9A-F])+)`）。生の改行・記号が混入しないこと、元文字列へ完全復元できることを検証済み。改行は Outlook 対策で CRLF（`%0D%0A`）。

### 効果の実測（宛先 info@vill.hidaka.kochi.jp、件名なし）
| 本文 | safe | compact |
|---|---|---|
| 名前/連絡先/画像を添付 | 140B → 23mm | 80B → 18mm |
| 【お名前】【ご連絡先】※このメールに画像を添付してください。 | 320B → 31mm | 140B → **23mm（25mm角に収まる）** |

→ **compact なら、文面を削らず丁寧なままで 25mm 角に収まる**。日本語を生で含むQRも文字化けせずデコードできることを確認済み。

### compact の残リスク
規格上「文字コード指定なし」の状態のため、**ごく一部の古い読取アプリで文字化けする可能性**が残る。スマホ標準カメラ・主要アプリは UTF-8 を自動判別するので実用上は問題ないはず。文字化けする端末があれば safe に切り替える。

## 8. 画像サイズと印刷（mm と解像度）

### サイズ指定は px でなく実寸(mm)
- 常に300dpi相当・1マス最低4画素で描画。
- **「px を小さくする」は印刷品質を落とすだけなので採らない**。画素数は高いまま、紙の上の実寸(mm)だけを変える。

### 読み取れる最小サイズ
- スマホで確実に読めるのは **1マス0.4mm以上**。
- 推奨最小サイズ ＝ (モジュール数＋余白8) × 0.4mm。これを下回る大きさを選ぶと画面が警告する。
- 25mm角に収まるのはバージョン9（53マス）まで（容量 L=230 / M=180 バイト）。

### PNG への解像度埋め込み（pHYs）
- ブラウザが作る PNG には解像度情報がなく、Word は 96dpi とみなして大きく挿入してしまう。
- そこで PNG に **pHYs チャンク**（1メートルあたりの画素数・単位メートル）を手で書き込み、Word/Excel が指定 mm で貼り付くようにした。
- チャンク挿入後も全チャンクの CRC が正常であること、実寸どおりに貼り付く計算、デコード可能を検証済み。
- SVG は `width="25mm" height="25mm"` の実寸指定で出力。

## 9. 文書への貼り付け手順（Office 2016 / 買い切り版）

### クリップボードの限界（重要）
「画像をコピー → Ctrl+V」は手軽だが、**Windows のクリップボードは解像度情報を運べない**。OSが画像をビットマップに変換する際 pHYs が落ち、Word が96dpi扱いにするため**実寸の約3倍**で貼り付く（25mm→約75mm）。
→ ツールはコピー時に「貼り付けると約○mmになります」と実数を表示し、手動修正を促す。

### 確実な方法＝ファイル保存してから挿入
- **Office 2016 買い切り版は SVG 非対応**（SVG対応は Microsoft 365 版だけ）。確認は Word「ファイル」→「アカウント」。
- したがって **PNG を推奨**:
  1. 「PNG画像で保存」→ `QR_info_25mm.png`
  2. Word「挿入」タブ →「画像」→ ファイル選択 → 挿入
  3. 挿入後クリック →「図ツール/書式」→「サイズ」が 2.5cm になっていれば成功（違えば `2.5cm` と直接入力）
  4. 隅へ動かすには「文字列の折り返し」→「前面」→ドラッグ

### `.svg` が「HTMLドキュメント」と表示される件
Windows が `.svg` を Edge に関連付けていると「種類」欄が「Microsoft Edge HTML ドキュメント」と表示され、拡張子も隠れる。**中身は正しくSVG**（`<svg … width="25mm">`）。エクスプローラーの「表示」→「ファイル名拡張子」で `.svg` を確認できる。ただし Office 2016 では結局 PNG を使うのが無難。

## 12. 設計上の約束（変更時に守ること）

- 外部通信を一切足さない（`fetch`/CDN/外部スクリプト禁止）。更新のたび痕跡ゼロを確認する。
- バイト数は `payload.length`（文字数）でなく `QRGen.utf8Bytes(payload).length` で数える（compact だと多バイト文字が混ざるため）。
- ローカルと iCloud の2ファイルを同一に保ち、ハッシュ一致を確認する。
- 定型文 JSON の後方互換（version 1・2 を読めること）を壊さない。
