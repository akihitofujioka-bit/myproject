# 日報ツール 設計書

版 1.0／2026-09-28

この文書は「このツールが何を、どういう考えで、どう動かしているか」を、次の担当者や
手直しする人が読めるようにまとめたものです。使い方だけを知りたい場合は `README.md` を

---

## 1. 目的と割り切り

### 解決したい困りごと

日報・週報・月報は、書く材料そのものはすでに手元にあります。

- 打ち合わせのときに手で書いたメモ（紙・写真）
- 配られた Word・Excel の資料
- 会議の録音

困るのは「材料はあるのに、report の形に組み直すのが面倒」という点です。
このツールは **材料をフォルダに放り込むだけで、下書きの形まで持っていく**ことだけを目的にしています。

### 3 つの割り切り

| 割り切り | 理由 |
|---|---|
| **要約しない。** LLM を使わず、語句の一致で節に振り分けるだけ | 個人情報を含むメモを外に出せない（後述）。手元で動く小さな模型では、要約は誤りが混ざる。**言い換えないので、書いてあることは必ず元のまま** |
| **出力は下書き。** そのまま提出する前提にしない | 振り分けは機械的なので取り違えがある。人が直すことを文書の中にも書いてある |
| **追加の道具をなるべく増やさない。** OCR は OS 標準のものを使う | 役場のパソコンはインターネットにつながらない。Tesseract のような外から入れるものは避ける |

### なぜ「要約しない」を選んだか

議事録や打ち合わせメモには、人事・評価・給与のような外に出せない話が混ざります。
クラウドの AI に投げるのは論外として、手元の小さな模型に要約させても、
**元の文になかったことを書く**危険が残ります。行政の文書でそれは困ります。

そこで「拾う・振り分ける・並べる」だけにして、**文章そのものは 1 字も変えない**ことにしました。
そのぶん出力は粗いので、「下書き」と割り切っています。

## 2. 全体の流れ

```
 素材/ にファイルを入れる（サブフォルダ可）
      │
      │ ① 走査（scan_inbox）
      │ ② 日付を決める（detect_datetime）★§4
      │ ③ 文字を取り出す（extract）★§5   ─── .cache/ に保存。同じファイルは二度処理しない
      ▼
   Material（ファイル・日時・取り出した文字）の一覧
      │ ④ 行に割り、分類して組み立てる（build_daily）★§6
      ▼
   日報/2026-09-21.md
      │ ⑤ 日報を読み戻す（parse_report）★§7 ─── 手で直した内容もそのまま拾う
      ▼
   週報/2026-W39.md ／ 月報/2026-09.md
```

**⑤ で日報を読み戻すのが要点です。** 週報は素材からではなく**日報から**作るので、
日報を手直ししてから週報を作り直すと、直した内容が反映されます。

## 3. フォルダの持ち方

```
~/日報/                      ← config.json の workspace（環境変数 NIPPO_WORKSPACE が優先）
  素材/                      ← ここにファイルを入れる
    2026-09-21_打合せメモ.jpg
    2026-09-21/録音.m4a      ← フォルダ名で日付を指定してもよい
  日報/2026-09-21.md
  週報/2026-W39.md
  月報/2026-09.md
  .cache/                    ← 文字取り出しの結果（JSON）
```

素材は**消しません**。日報を作り直したいときのために残します。
`.cache/` があるので、同じファイルを何度走査しても読み取りは 1 回だけです。

## 4. 日付の決め方（`detect_datetime`）★

素材を「何日の分か」に振り分けるのが、このツールの最初の関門です。
**確かなものから順に**見て、最初に見つかったものを採用します。

| 順 | 手がかり | 例 | 根拠として表示 |
|---|---|---|---|
| 1 | **ファイル名** | `2026-09-21_打合せ.jpg`、`20260921_進捗.xlsx` | ファイル名 |
| 2 | **親フォルダ名**（素材フォルダの直下まで遡る） | `素材/2026-09-21/録音.m4a` | フォルダ名 |
| 3 | **写真の撮影日時**（EXIF） | スマホで撮ったメモ | 撮影日時 |
| 4 | **録音の作成日時** | ボイスメモ | 録音日時 |
| 5 | ファイルの作成日時 | それ以外 | ファイル作成日時 |

`2026-09-21` `2026/9/21` `20260921` `2026年9月21日` を認識し、後ろに `14:30` `14時30分` が
続いていれば時刻も拾います。

**どの根拠で判定したかを、日報の素材欄に必ず書きます**（「日付の根拠: 撮影日時」）。
自動判定は外れることがあるので、**外れたことに気づけるようにする**ためです。
画面の「この日の素材を確認」でも、作る前に一覧で確かめられます。

## 5. 文字の取り出し（`extractors.py`）

### 5.1 OS ごとの使い分け

**OCR と文字起こしは、その OS に最初から入っているものを使います。**
追加のインストールを増やさないためです。

| 処理 | macOS | Windows 10/11 |
|---|---|---|
| 画像の OCR | Vision（`ocr_helper.swift` を初回だけ `swiftc` で組み立て） | Windows.Media.Ocr（`ocr_windows.ps1` を PowerShell 経由で呼ぶ） |
| PDF の OCR | PDFKit | PyMuPDF でページを画像にしてから OCR |
| `.doc`（旧 Word） | `textutil` | `doc97.py`（`gikai_simple` から複製） |
| `.rtf` `.odt` | `textutil` | **未対応**（`.docx` にして入れる） |
| 撮影日時 | `sips` | Pillow の EXIF |
| 音声の文字起こし | Whisper（ローカル） | **未対応**（文字起こし済みの `.txt` を入れる） |

Windows の OCR は 1 文字ごとの確からしさを返さないので、確度は 0.8 の固定値にしています
（macOS の Vision は実際の値を返す）。

### 5.2 キャッシュ（`.cache/`）

OCR も文字起こしも時間がかかるので、結果を JSON で保存します。

鍵は **パス＋ファイルの大きさ＋更新時刻の SHA-1**（`_cache_key`）です。ファイルを差し替えれば
鍵が変わるので、自動で読み直されます。

**失敗した結果はキャッシュしません**（`if not cached.get("error")`）。
一時的な失敗（Swift の組み立て待ちなど）を引きずらないためです。

### 5.3 1 件の失敗で止めない

読み取りは 1 ファイルずつ `try` で囲み、失敗しても `error` を記録して次へ進みます。
失敗したファイルは日報の「確認してほしい点」に名前と理由が載ります。

**20 件のうち 1 件が読めなくても、残り 19 件で日報ができるほうが役に立つ**という判断です。

## 6. 分類と日報の組み立て（`reporter.py`）★

### 6.1 行に割る（`split_lines`）

取り出した文字を「1 項目 1 行」にします。

- 行頭の記号（`-` `・` `①` `(1)` など）を落とす（`_BULLET`）
- **60 字を超える行は「。」で分ける**（手書きメモが 1 行に続いていることがあるため）
- 2 字未満の行、日付や時刻だけの行（`_DATE_ONLY`）は捨てる

### 6.2 4 つの節に振り分ける（`classify`）

`config.json` の `classify` にある語句を含むかどうかだけで決めます。
**優先順は 課題 → 明日の予定 → 会議 → その他**です。

| 節 | 語句の例 |
|---|---|
| 課題・相談事項 | 課題・懸念・相談・要確認・未了・保留・TODO・遅れ |
| 明日の予定 | 明日・来週・予定・締切・期限・までに |
| 会議・打ち合わせ | 会議・打合せ・協議・面談・委員会・説明会・来庁 |
| その他の業務 | （どれにも当たらないもの） |

「課題」を最優先にしているのは、**見落とすといちばん困るのが課題だから**です。
「明日の打ち合わせの準備が未了」のような行は、会議ではなく課題として上がります。

語句は職場の言い回しに合わせて `config.json` に足せます。

### 6.3 長い素材の扱い

会議資料の Excel などを全部載せると、日報が資料のコピーになってしまいます。

- **20 行を超える素材（`longSourceLines`）は「長い」とみなす**
- 長い素材からは、**語句に一致した行だけ**を本文に載せる（「その他の業務」行は載せない）
- それも **15 件まで（`maxHitsPerLongSource`）**
- 代わりに「内容が長いため語句に一致した行だけ上に載せた。全文は下の素材欄」と書く

**全文は必ず素材欄に載る**ので、情報は失われません。上に出すものを絞っているだけです。

### 6.4 個人情報を含む行を落とす

`config.json` の `privacy.excludeTopics`（既定: 人事・評価・給与・報酬・契約条件）を含む行は、

- **本文に転記しない**
- **素材欄でも「（非公開の議題のため省略）」に置き換える**
- 代わりに「非公開の議題あり（○行を省略）」とだけ書く

素材欄でも省略するのが要点です。**日報ファイルそのものに残さない**ためで、
日報を誰かに見せるときに気をつける必要をなくしています。

### 6.5 重複を落とす

同じ内容が複数の素材に出てくる（配布資料と自分のメモなど）ことがあるので、
**空白と句読点を除いた文字列**が同じ行は 2 回目以降を捨てます。

### 6.6 日報の形

```markdown
# 日報 2026-09-21（月）

## 会議・打ち合わせ
- …
## その他の業務
## 明日の予定
## 課題・相談事項

---
### 確認してほしい点（報告書には含めない）
- 「メモ.jpg」の OCR 確度が低め（0.38）。誤読がないか原文と照合してください
- 各節への振り分けは語句の一致による機械的なもの（設定 classify）。取り違えがあれば直してください

### 素材（3件）
#### 1. 14:30 打合せメモ.jpg（画像 → OCR、確度 0.72、日付の根拠: 撮影日時）
> （取り出した文字の全文）
```

**`---` から下は報告書に含めない**という取り決めです。見出しにもそう書いてあります。
週報を作るときも `---` より上だけを読みます（§7）。

- 節が空なら「記録なし」「特になし」と書く（空欄のまま出さない）
- 振り分けが機械的であることを、**毎回必ず文書の中に書く**（下書きだと分かるように）

## 7. 週報・月報（`parse_report`）

週報・月報は**素材からではなく、日報の Markdown から**作ります。

```
日報/2026-09-21.md ─ parse_report ─┐
日報/2026-09-22.md ─ parse_report ─┼→ build_weekly → 週報/2026-W39.md
…                                  ┘
```

`parse_report` は `---` より上の `## 節名` と `- 項目` を読み戻します。
**人が手で直した内容もそのまま拾う**ので、日報を直してから週報を作り直せば反映されます。
「記録なし」「特になし」「（…」で始まる行は拾いません（空欄を持ち上げないため）。

- 素材はあるのに日報が無い日は、週報・月報を作るときに**日報も自動で作ります**
- 課題・相談事項は週をまたぐと重複しがちなので、週報では**重複を落として**並べます
- 月報は週ごとにまとめます

既にある報告書は作り直しません。作り直すには `--force`（画面では確認のダイアログが出ます）。

## 8. 外に出さないための決まり

**このツールは、いかなる場合もネットワークに出ません。**

| 処理 | どこで動くか |
|---|---|
| OCR | OS に最初から入っているもの（Vision / Windows.Media.Ocr）。どちらも端末内 |
| 音声の文字起こし | Whisper。モデルをこのパソコンに置いて動かす |
| 分類・要約 | 語句の一致だけ。**LLM を使わない** |
| 送信 | **一切しない**（`urllib` も `requests` も使っていない） |

手書きの打ち合わせメモには住民や職員の名前が入ります。この前提を崩す変更
（クラウドの OCR や AI 要約を足すなど）は、**入れてはいけません**。

## 9. 画面とコマンド（`nippo.py`）

Tkinter のボタン画面です。日付を入れて「日報を作る」「週報を作る」「月報を作る」。

```
python3 nippo.py                     # 画面
python3 nippo.py daily 2026-09-21    # 日報
python3 nippo.py weekly 2026-09-21   # その日を含む週（月〜日）
python3 nippo.py monthly 2026-09     # その月
python3 nippo.py list 2026-09-21     # 素材の一覧と日付判定だけ
python3 nippo.py extract <ファイル>   # 1 ファイルの文字取り出しを試す
```

`list` と `extract` があるのは、**うまくいかないときに原因を切り分ける**ためです。
日付がおかしいのか、文字が取り出せていないのか、分類が外れているのかを順に確かめられます。

起動は macOS が `日報ツール.command`、Windows が `日報ツール.bat`。

**`.bat` は Shift_JIS(CP932)・CRLF で保存し、`chcp` を書きません。**
CP932 で保存したファイルの先頭で `chcp 65001`（UTF-8）にすると、それ以降の日本語が
すべて化けます（実際に起きました）。

## 10. テスト

```
python3 test_reporter.py
```

3 件。組み立て部分（`reporter.py`）だけを見ています。

| テスト | 見ているもの |
|---|---|
| `test_split_and_classify` | 行への割り方と 4 節への振り分け |
| `test_daily_and_parse` | 日報の組み立てと、それを読み戻せること |
| `test_weekly_monthly` | 週報・月報の束ね方 |

文字の取り出し（`extractors.py`）は OS の機能に依存するため自動テストがありません。
`python3 nippo.py extract <ファイル>` で 1 件ずつ手で確かめます。

## 11. 動作環境と既知の制約

### macOS

- `/usr/bin/python3`
- `python-docx`・`openpyxl`・`openai-whisper`
- `ffmpeg`（音声用）
- `swiftc`（Xcode か Command Line Tools）。OCR の補助プログラムを初回だけ組み立て、`.build/` に置く

### Windows 10/11

- Python 3.9 以降（配布 zip の `wheels` は **3.11・64 ビット専用**）
- `python-docx`・`openpyxl`・`pillow`・`pymupdf`（`部品のインストール.bat` で入る）
- OCR は追加インストール不要

### 制約

| 制約 | 理由・回避 |
|---|---|
| 音声の文字起こしは **macOS のみ** | Whisper が重い。Windows では文字起こし済みの `.txt` を入れる |
| `.rtf` `.odt` は **macOS のみ** | `textutil` に頼っている。`.docx` にして入れる |
| 旧 `.xls` は読めない | `.xlsx` で保存し直す |
| 振り分けは語句の一致だけ | 取り違えがある前提。文書にもそう書いてある |
| 行数・確度は目安 | OCR の確度が低いときは注意書きが出る（既定 0.45 未満） |

### まだ確かめていないこと

**Windows での動作は実機で未確認です。** `部品のインストール.bat`、`ocr_windows.ps1`、
画面の見た目、手書き OCR の当たり具合。役場のパソコンで一度通してください。

## 12. 変えたくなったら

| 変えたいこと | 場所 |
|---|---|
| 作業フォルダ | `config.json` の `workspace`（環境変数 `NIPPO_WORKSPACE` が優先） |
| 節に振り分ける語句 | `config.json` の `classify`（職場の言い回しを足す） |
| 転記しない話題 | `config.json` の `privacy.excludeTopics` |
| 長い素材の境目 | `config.json` の `longSourceLines`（既定 20）・`maxHitsPerLongSource`（既定 15） |
| OCR 確度の警告の線 | `config.json` の `ocr.lowConfidence`（既定 0.45） |
| 文字起こしの精度 | `config.json` の `whisper.model`（`base`〜`large-v3`）。`initialPrompt` に固有名詞を並べると誤変換が減る |
| できた報告書を開くアプリ | `config.json` の `openWith`（既定 `TextEdit`。`Obsidian` なども可） |
| 節の名前・並び | `reporter.py` の `DAILY_SECTIONS` / `SECTION_OF` |

## 13. `/report` スキルとの関係

このリポジトリには、PLAUD とカレンダーから日報を作る `/report` スキル（`reports/daily/`）もあります。

| | `/report` スキル | 本ツール |
|---|---|---|
| 材料 | PLAUD の文字起こし・Google カレンダー・GitHub | **手元のファイル**（写真・Word・Excel・音声） |
| 動く場所 | Claude（オンライン） | **このパソコンの中だけ** |
| 出力先 | `reports/daily/` | `~/日報/`（**混ざらないように分けてある**） |

**書式は `/report` の日報に合わせてあります**（同じ 4 節）。
ネットにつながる場面では `/report`、つながらない場面・手書きメモが主な場面では本ツール、
という使い分けです。

`doc97.py` は `gikai_simple` からの複製です。どちらのツールも単体で配れることを
優先し、あえて共有していません。
